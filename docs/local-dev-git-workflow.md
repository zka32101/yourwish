# ローカル開発 Git 運用ガイド

ローカル(Windows等)でビルド・テスト・修正を繰り返す際の Git 運用指針。

## 基本方針

こまめにローカルコミット → 動作確認済みの単位で GitHub に push する。
ローカルコミットだけでは PC 故障・誤操作で作業が消えるリスクがあるため、
必ず GitHub に保存する。

## 基本フロー

1. 作業用ブランチを切る（`main`/`master` に直接コミットしない）
2. **作業前に必ず `git status` を確認** — ブランチ切り替え前に未コミットの
   変更があれば `git stash push -u` で退避してから切り替える
3. **ブランチの PR が既にマージ済みなら、そのブランチに積み増さず作り直す**
   ```bash
   git fetch origin main
   git checkout -B <ブランチ名> origin/main
   ```
   古いマージ済み履歴の上に新しい作業を乗せない
4. ビルド/テストが通った「動く単位」でローカルコミット
5. push 前に一度クリーンな状態でビルドし直す（キャッシュに騙されない）
   ```bash
   flutter clean
   rm -f pubspec.lock
   rm -rf .dart_tool/
   flutter pub get
   ```
6. 数コミット貯まった、または区切りが良いタイミングで push
   ```bash
   git push -u origin <ブランチ名>
   ```

## push 頻度のトレードオフ

- 毎回 push: クラウド保存で安心。履歴は細かくなる
- 貯めてから push: 履歴はきれいだが、push 前に PC が壊れると未 push の分は失う
- 目安は「動く単位（1つのビルド/テストが通った時点）」でコミットし、
  ローカルに数回貯めたら push

## Flutter/Dart プロジェクトで踏んだ落とし穴

- `.freezed.dart` / `.g.dart` などの自動生成ファイルは **コミットしない**
  （`.gitignore` に追加）。コミットされて残ると、後から正しいコードに
  直しても生成物が古いまま残り、CI が延々と落ち続ける原因になる
- freezed 3.x 系では `class X` ではなく **`abstract class X`** と書く
  （2.x 系との破壊的変更。書き忘れると `toJson` 未実装エラーになる）
- `pubspec.yaml` のバージョン制約は広すぎると逆に危険（例:
  `json_annotation: ^4.9.0` のような緩い指定が原因で、build_runner が
  一部ファイルの生成を静かにスキップする事例があった）
- 削除・上書き系の git 操作（`checkout`, `reset --hard` など）の前は
  必ず `git status` で今の変更を確認してから実行する

## 一般的に入れておくとよい観点

### コミット関連
- コミットメッセージは「何を」より「なぜ」を書く（What は diff を見ればわかる）
- 1 コミット = 1 つの意味のある変更（無関係な修正を混ぜない）
- APIキー・パスワード・`.env` などの秘密情報は **絶対にコミットしない**
  （`.gitignore` に最初から入れておく。誤って push した場合は
  差し替え必須。履歴から消すだけでは不十分）

### ブランチ運用
- ブランチ名に用途がわかる接頭辞をつける（`fix/`, `feature/`, `local/` など）
- 長期間更新しないブランチは定期的に `main`/`master` を取り込んで
  コンフリクトを早期発見する
- 完了したブランチは削除する（放置すると管理が煩雑になる）

### push 前のチェック
- `git diff --cached` で意図しないファイル（ビルド成果物、IDE 設定、
  一時ファイル）が混ざっていないか確認
- lint/format は CI で落ちる前にローカルで実行
- 大きすぎる変更は分割して PR を出す（レビューしやすく、問題発生時の
  切り分けも楽）

### バックアップ・復旧
- 大きな変更の前は `git tag` や別ブランチで現状のスナップショットを残す
- `git reflog` は誤って reset した場合の最後の砦（消しても実は復旧
  できることが多い）

### その他
- `.gitignore` は言語/フレームワークの標準テンプレートを最初に導入する
  （後から漏れに気づくのは大体手遅れ）
- CI（自動テスト）を通さずに `main`/`master` へ直接マージしない運用に
  しておくと事故が減る
