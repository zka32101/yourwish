# マルチセッション統合オーケストレーター

## 概要

複数の Claude Code Remote セッションを一元管理し、自動進行させるオーケストレータースキル。親セッションが子セッションの状態を監視し、次に進められるセッションに自動指示を送信します。

## 主な機能

### 1. セッション自動検出
- 全セッションを定期的に list_sessions で検出
- 新規セッションを自動登録
- セッション状態を追跡（RUNNING, IDLE, BLOCKED, ARCHIVED, REVIEW_READY）

### 2. 自動指示配信
- `create_trigger()` で特定セッション宛の指示をスケジュール
- `persistent_session_id` で同じセッションに繰り返し指示
- UTC タイムスタンプで正確な実行タイミング制御

### 3. ループ継続実行
- `/loop` + `ScheduleWakeup()` で 5 分ごと自動実行
- セッション状態を継続監視
- 新規セッション検出時に自動トリガー作成

### 4. 放置セッションの防止（重要）
トリガーは1回きり（run_once_at）で実行されるため、指示を送った後にセッションが再び判断待ちになっても、次に誰かが気づかない限り**永久に停止したまま**になる。「直近の変化」だけを見る軽量巡回では、何時間も前からBLOCKEDのセッションを見逃す。

- 軽量巡回（毎時）は直近の変化のみチェックしてよいが、**数時間に1回（目安: 4〜6時間ごと）は全BLOCKEDセッションを棚卸しする**
- 棚卸しでは `status_bucket` が BLOCKED/REQUIRES_ACTION の全件を対象に、直近の更新時刻に関わらず内容を確認する
- 各セッションを以下に分類し、対応可能なものは即座にトリガーを送る:
  - **カテゴリA（ユーザー対応必須）**: 秘密情報・外部認証・ローカルマシン操作が必要 → 保留のまま、まとめて定期報告
  - **カテゴリB（自動対応可能）**: 単純な選択・方向性の質問 → 判断して指示トリガーを送る
  - **カテゴリC（マージ承認待ち）**: GitHubマージ判断 → ユーザーに報告
  - **カテゴリD（要確認）**: 内容が不明瞭 → 詳細確認してから分類

## 対応方針

### 簡単な質問
親セッションが自動回答 → 子セッション続行

例：
- 「次のステップは？」 → 「〇〇を実装してください」と自動回答
- 「これでいい？」→ 「はい、進めてください」と自動回答

### 難しい決定
親セッションから一旦停止 → ユーザーに確認

例：
- 「アーキテクチャをAとBどちらにする？」 → ユーザーに相談
- 「この修正を本番に含めていい？」 → ユーザーに確認

### ユーザー回答待ちで進まない場合
一旦保留にする。無理に進めず、他の進行可能なセッションを優先して処理する。保留セッションは定期的に再確認する。

### 承認作業の代行
技術的な検証で判断可能なものはオーケストレーターが自動承認して次へ進める。ビジネス判断・設計判断が必要なものはユーザーに確認する。

**自動承認可能:**
- テスト合格、ビルド成功、コード品質OK、セキュリティ基準達成、バグ修正完了、見た目/操作性改善の検証完了

**ユーザー確認が必要:**
- アーキテクチャ変更、主要機能の削除/変更、本番環境リリース、大規模UI変更、セキュリティ脆弱性の対応方針、ユーザーデータ扱いの変更

### GitHubマージの扱い
マージ判断が必要な項目（PR番号・リポジトリ・変更概要・CI状態）を検出したら、自動マージはせず必ずユーザーに報告してから対応する。

## 自動改善サイクル（開発が一通り進んだセッション向け）

開発が一通り完了したセッションには、以下の観点で改善を継続的に指示する。

### 基本方針
1. **競合比較 → 差別化実装**: 同カテゴリの競合アプリ/ゲームと比較し、機能・コンテンツの不足や差別化要素を洗い出して追加実装する
2. **リアル性向上**: リアルさが重要なゲーム（シミュレーション系など）は、よりリアルな挙動・表現に改善する
3. **使い方説明画面の追加**: 操作方法・ルールを説明する画面を実装する
4. **アップデート内容の表示**: 更新履歴・変更内容をユーザーに見せる画面/通知を実装する
5. **改善要望/バグ報告画面の実装**: ユーザーがフィードバックを送れる導線を実装する

### 追加観点

**ユーザー定着・成長**
- チュートリアル/オンボーディング（初回起動時の導線）
- プッシュ通知/リテンション施策
- レビュー・評価促進導線（適切なタイミングでのストア評価リクエスト）
- SNS共有機能（スコア・実績のシェア）

**ゲーム特有**
- 季節イベント/定期コンテンツ追加（継続プレイの動機付け）
- 実績/コレクション要素（やり込み要素）

**品質・信頼性**
- クラッシュ/エラーログ収集体制（Crashlytics等）
- パフォーマンス最適化（起動速度・メモリ・バッテリー消費）
- 古い端末/低スペック対応確認
- オフライン対応（ネットワーク不安定時の挙動）

**アクセシビリティ・グローバル対応**
- 多言語対応（ローカライズ、海外展開の可能性がある場合）
- 文字サイズ/色覚対応

**収益・法務**
- 広告/IAPバランス見直し（収益と体験のバランス最適化）
- プライバシーポリシー整合性（実装内容とポリシー記載の一致確認）
- ストア掲載情報最適化（ASO：スクリーンショット・説明文の改善）

**データ保護**
- データバックアップ/引き継ぎ機能（機種変更対応）

### 過去の課題管理
過去の課題・問題は情報として保存し、再発しづらいようにする（例: リポジトリ内にトラブルシューティング記録やナレッジベースを整備）。

### その他
上記に当てはまらない気づいた改善点も、オーケストレーターの判断で改善提案・実装する。

## 設定と起動

### 親セッションで設定
```bash
# リポジトリをマウント（chess と yourwish）
# /loop で自動実行開始
```

### トリガー作成（UTC 時刻）
```javascript
// 子セッションへの指示スケジュール
create_trigger({
  name: "Auto: [セッション名] [タスク名]",
  prompt: "[具体的な指示]",
  persistent_session_id: "session_XXXXX",
  run_once_at: "2026-08-29T06:00:00Z"
})
```

### Loop 継続
```bash
# ScheduleWakeup で 5 分ごと再実行
ScheduleWakeup({
  prompt: "マルチセッション自動進行 - 未管理セッション検出と自動指示",
  delaySeconds: 300,
  reason: "Detect unmanaged sessions and send instructions"
})
```

## セッション状態管理

| 状態 | 説明 | 対応 |
|------|------|------|
| **RUNNING** | 実行中 | 監視継続 |
| **IDLE** | 待機中 | 次のタスク指示 |
| **BLOCKED** | 停止中（ユーザー待ち） | 確認後再開指示 |
| **REVIEW_READY** | 確認待ち | レビューコメント反映指示 |
| **ARCHIVED** | 完了/終了 | 新トリガー不要 |

## トリガー管理

### 作成済みトリガー確認
```javascript
list_triggers({ limit: 50 })
```

### トリガー削除（破損時）
```javascript
delete_trigger({ trigger_id: "trig_XXXXX" })
```

### トリガー更新（スケジュール変更）
```javascript
update_trigger({
  trigger_id: "trig_XXXXX",
  prompt: "[新しい指示]",
  cron_expression: "0 */6 * * *"  // 6時間ごと
})
```

## ベストプラクティス

### タイムスタンプ
- 常に **UTC** 使用（タイムゾーン混在防止）
- 現在時刻 +5分以上先に設定
- 例: `2026-08-29T06:22:00Z`

### トリガー命名
```
Auto: [セッション名] [タスク説明]
例: Auto: Chess Phase D 80%+ テストカバレッジ確認
```

### 応答判定
- **簡単**: 明確な指示、Yes/No判断、単純な問題解決
- **難しい**: アーキテクチャ判断、リスク判断、ビジネス判断

### エラーハンドリング
- セッション消失時 → トリガー自動無効化（`ended_reason: auto_disabled_session_gone`）
- 過去日時トリガー → 手動削除 + 再作成
- ネットワーク遅延 → 最大 4 回リトライ（2s → 4s → 8s → 16s）

## トラブルシューティング

| 問題 | 原因 | 解決 |
|------|------|------|
| トリガー実行されない | 過去の日時 | `update_trigger` で新しい日時に変更 |
| セッション検出されない | 親セッションの権限不足 | リポジトリアクセス権確認 |
| ループ停止 | コンテキスト上限 | `ScheduleWakeup` で再開 |
| 子セッションアクセス失敗 | `persistent_session_id` 誤り | `list_sessions` で正確なID確認 |

## Claude リソース節約運用

セッション数・トリガー数が増えるほどトークン消費とコストが増大するため、以下を徹底する。

| 項目 | 対策 |
|------|------|
| **/loop 間隔の可変化** | 変化がない時（noop）は 5分 → 15〜30分に自動延長。新規セッション検出・トリガー発火直後など動きがある時のみ5分に戻す |
| **Agent乱発の抑制** | 単純な状態確認（list_sessions/list_triggersの結果を見るだけ等）は直接ツール呼び出しで済ませ、複雑な分析・分類・大量トリガー作成のみAgentに委任する |
| **トリガー統合** | 同一セッションに対する重複トリガーを作らない。複数の確認事項があればまとめて1つのトリガー/指示に統合する |
| **完了セッションのアーカイブ** | 開発完了・長期未更新のセッションは ARCHIVED 化し、監視対象（/loopの巡回対象）から除外する |
| **モデル選択** | 進捗確認・分類などの軽作業は軽量モデル、複雑な実装判断・設計提案のみ上位モデルを使う |
| **重複読み込みの回避** | 同じセッション情報・ファイルを同一ループ内で何度も取得しない。結果はその場で使い切る |
| **バッチ処理優先** | 個別セッションずつ確認するのではなく、list_sessions/list_triggers 等の一括APIをまず使い、必要な差分のみ深掘りする |
| **出力の簡潔化** | 監視レポートは変化があった項目のみ詳細を書き、変化なしはサマリー1行に留める |

## セキュリティチェック

各セッションの開発が一通り進んだら、定期的にセキュリティチェックを指示し脆弱性を減らす。

- `security-review` / `app-privacy-security` スキルを活用した脆弱性スキャンを指示
- 依存パッケージの既知脆弱性（CVE）確認
- API鍵・認証情報・秘密鍵のハードコード検出
- 発見した脆弱性は重大度に応じて対応：
  - **軽微**（依存更新等）→ 自動修正して次へ進める
  - **重大**（認証情報漏洩、権限設計の欠陥等）→ 修正案とともにユーザーに報告

## 暴走防止（破壊的操作の制御）

以下の操作は**自動承認の対象から常に除外**し、子セッションが提案・実行しようとした場合は必ずユーザー確認を挟む。オーケストレーター自身もこれらを直接実行しない。

- `DROP TABLE` / `DELETE FROM`（条件なし・広範囲の削除）などの破壊的DB操作
- `rm -rf` 等の広範囲ファイル削除
- `git push --force` / `git reset --hard`（共有ブランチに対して）
- 本番データベースへのマイグレーション（データ消失を伴うもの）
- ユーザーデータの一括削除・匿名化解除
- Firestore/Storage 等のバケット・コレクションの削除

**運用方法:**
- 子セッションへの自動指示には「上記の破壊的操作は実行せず、必要であれば内容をまとめて報告するだけに留める」旨を含める
- 該当操作の提案を検出した場合、/loop はそれを実行せず、次回オーケストレーターからユーザーへ確認する

## ユーザーへの確認タイミング

オーケストレーター自身の判断で対応できない事項（アーキテクチャ判断、破壊的操作の要否、リリース可否など）が生じた場合は、都度このチャット（親セッションとの会話）で確認を依頼する。トリガー経由で子セッションに答えを流すのではなく、まずここでユーザーに聞く。

- 確認は溜め込みすぎず、判断が必要になった時点でその都度行う
- 複数件ある場合はまとめて一度に確認してよい
- 緊急度の低い確認は次回の監視レポートに含めてよいが、破壊的操作や重大なセキュリティ問題は即時報告する

## 報告時のリンク併記

PR・セッション・トリガーなどに言及する際は、番号/名前だけでなく実際のURLも併記する。

- GitHub PR/Issue → `https://github.com/<owner>/<repo>/pull/<番号>` または `/issues/<番号>`
- セッション → `https://claude.ai/code/session_XXXXX`（session_id から構築、または get_session の返り値を利用）
- Artifact/ダッシュボード → 発行時に得られる URL

例: 「PR #11 (zka32101/yourwish) → https://github.com/zka32101/yourwish/pull/11」
