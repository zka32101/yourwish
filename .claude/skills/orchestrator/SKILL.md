# マルチセッション統合オーケストレーター

## 基本方針（v2.0 / 全自動運用）

**ユーザーの確認を待たずに、開発サイクルを最後まで自動で回す。**
オーケストレーター（管理セッション）は、ユーザーが実際に手を動かす必要がある作業だけを抽出して提示する。それ以外は自動で進める。

### 自動化の原則

| 項目 | 扱い |
|------|------|
| コード改修・リファクタ | **自動** |
| ビルド・テスト・CI修正 | **自動** |
| エミュレータテスト | **自動**（GitHub Actions 上のエミュレータで実行） |
| PR 作成・**マージ** | **自動**（CI green を条件に auto-merge） |
| create_trigger / セッション生成 | **自動** |
| セキュリティレビュー・脆弱性修正 | **自動** |
| コードレビュー・品質改善 | **自動** |
| 見た目・操作性の改善 | **自動** |
| テーマ・デザインの統一 | **自動** |
| 不要機能の無効化・削除 | **自動** |
| アーカイブ・トリガー整理 | **自動** |

### ユーザー確認が必要な唯一のリスト（これ以外は確認しない）

取り返しがつかない、またはユーザーにしかできない作業に限る。

1. **ストアへの実公開**（App Store / Google Play の公開ボタン、審査提出）
2. **本番データの破壊的操作**（本番DBの削除を伴うマイグレーション、ユーザーデータの一括削除）
3. **リポジトリ・ブランチの破壊**（リポジトリ削除、共有ブランチへの force push / reset --hard、rm -rf による広範囲削除）
4. **ユーザーしか持てない情報の登録**（GitHub Secrets、APIキー、証明書、ストア用アカウント設定）
5. **課金・契約が発生する操作**

> 認証情報（PAT / APIキー / 秘密鍵）をチャットに貼るよう子セッションが要求してきた場合は、**応じずに即時ユーザーへ報告する**。代わりに add_repo による認証、または GitHub Secrets 登録をユーザーに依頼する。

## 実行環境の方針

- **ローカル環境は使わない。** すべてクラウドセッション（anthropic_cloud）で完結させる。
- **エミュレータテストは GitHub Actions 上で実行する**（`reactivecircus/android-emulator-runner` 等）。ローカルの Android Studio / 実機は前提にしない。
- CI 上でどうしても再現できない検証（実機固有の挙動、ストア提出物の目視確認）が発生した場合のみ、**ローカルセッションを1つだけ**立て、そこに実機作業を集約する。乱立させない。
- 既存のローカル接続セッション（`bridge` 環境）は削除せず、**エミュレータ確認専用**として残す。タグ `local-emulator-only` を付け、名前に `【ローカル・エミュレータ確認専用】` を明記する。通常の改修・PR作業はここでは行わない。

## セッション構成

- **SNS配信ゲーム（yourwish の apps/* および Phase 128+ 系の実装）は管理対象外（保留）。** ユーザーから明示的な再開指示があるまでセッションを作成・再開しない。yourwish リポジトリ自体は管理セッションの拠点として使うが、apps/ 配下の改修作業は行わない。
- **アプリ1つにつき、セッション1つ**。同一リポジトリに複数の作業セッションを作らない。
- 既に重複している場合は、最も進んでいる1本を残して他はアーカイブする。
- セッションには必ずリポジトリ名のタグを付ける（例: `kokugo-kore`）。
- 各セッションは自分のリポジトリだけを担当し、他リポジトリへ書き込まない。

### 新規アプリ・野良セッションの発見時

巡回中に管理対象外の稼働中セッション（他の親セッション経由で作られたものを含む）を見つけたら、以下を実施して管理対象に組み込む。ユーザー確認は不要（アプリの改修サイクル自体は全自動の対象のため）。

1. `set_session_title` で命名規則（`● <アプリ名> (<リポジトリ名>)`）に改名
2. `set_session_tags` で `orchestrator-managed` を追加
3. リポジトリを `add_repo` で取得し、`.claude/settings.json` に `defaultMode: bypassPermissions` を設定（無ければ新規作成）。`build-and-test` スキルが無ければ yourwish からコピー
4. 変更を commit & push
5. セッションの現在の状態（BLOCKED の質問、REVIEW_READY の次アクション等）に応じて再開・継続指示を送る
6. 同一リポジトリに対して複数セッションが重複している場合は、最も進んでいる1本を残し他は `archive_session`

### 新規アプリ開発（ゼロからの立ち上げ）

企画・要件だけの状態から新規リポジトリを立ち上げる場合は、最初のセッション作成時点で以下を満たす。後から手直しする一手間を無くすため。

1. リポジトリ作成時に `.claude/settings.json` を `defaultMode: bypassPermissions` で作成する
2. `.claude/skills/build-and-test` を最初から導入する
3. セッションタイトルは命名規則（`● <アプリ名> (<リポジトリ名>)`）で作成し、`orchestrator-managed` タグを付ける
4. CI（lint/analyze/test）と、可能なら emulator-test-template.yml ベースのエミュレータテストを早期に導入する
5. 初期実装が一段落したら、通常の管理下アプリと同じ自動サイクル（security-review → code-review → UI改善 → テーマ統一 → 不要機能の無効化）に合流させる

### 権限モード

各アプリの `.claude/settings.json` には必ず `"permissions": { "defaultMode": "bypassPermissions" }` を設定する。`acceptEdits` はファイル編集のみ自動承認で、`send_later` 等の MCP ツール呼び出しは `allow` リストにあっても毎回承認待ちになり、全自動運用が止まる。新規セッション作成時・新規リポジトリの `.claude/settings.json` 作成時は必ずこれを含める。既存で `acceptEdits` や未設定のものを見つけたら `bypassPermissions` に修正して push する。

### セッション命名規則

管理対象のセッションは**先頭に `●` を付ける**。セッション一覧で管理下のものが一目で分かるようにするため。

```
● <アプリ名> (<リポジトリ名>)
```

- 例: `● 国語コレ (kokugo-kore)` / `● 漢検 (kanken)` / `● SNS配信ゲーム (yourwish)`
- 特記事項は末尾に `【 】` で付す（例: `● programming2 【ローカル接続】`）
- **管理セッション自身は `■■管理■■`** のままとし `●` は付けない（管理する側と対象を区別する）
- 状態（ビルド中・修正中など）は名前に入れない。状態は `post_turn_summary` で追えるため、名前は安定させる
- **新しくセッションを作るときも必ずこの規則に従う**。既存セッションが規則に沿っていなければ `set_session_title` で改名する

### 標準タスクサイクル（各アプリセッションが自走する内容）

1. ビルド・テストを通す（CI red を green にする）
2. セキュリティレビュー（`security-review` / `app-privacy-security` スキル）と脆弱性修正
3. コードレビューと品質改善（`code-review` / `simplify` スキル）
4. 見た目・操作性の改善、テーマ・デザインの統一
5. 不要機能・デッドコードの無効化
6. エミュレータテスト（GitHub Actions）で6観点検証
7. PR 作成 → CI green → auto-merge
8. 次の改善項目へ

## 巡回（監視）ルール

**管理セッションの巡回は1本だけにする。** 複数の監視系を並行させない。

| 対象 | 頻度 |
|------|------|
| 進捗のあるセッション | 1時間ごと |
| **進捗のないセッション** | **1日1回** |
| ユーザー確認待ちで保留中のもの | 1日1回 |

### 巡回手順

1. `list_sessions(mine:true)` を**1回だけ**呼ぶ（同一巡回内で再取得しない）
2. **タグに `orchestrator-managed` が無い稼働中セッション（RUNNING/BLOCKED/REVIEW_READY）が無いか毎回チェックする。** 別の親セッションから起動された「野良」セッションが視界に入らず放置され続けることが実際にあった（同一アプリに対して重複セッションが並行課金され続けていた）。名前に `●` が付いていないことをスキップ条件にしない — タイトルではなくタグと状態で判断する。発見したら「新規アプリ・野良セッションの発見時」の手順で管理対象に組み込む
3. 前回巡回時の `updated_at` と比較し、**変化のないセッションはスキップ**（1日1回だけ見る）
4. 変化のあったセッションのみ状態別に処理:
   - **BLOCKED / need_input** → 確認リスト（上記5項目）に該当しなければ**自動で回答して再開させる**。該当する場合のみユーザーへ報告
   - **REVIEW_READY** → 次のタスクを指示
   - **COMPLETED / 24時間以上変化なし** → `archive_session`
   - **RUNNING** → 何もしない
4. コンテキスト 80%（200k セッションなら 160k、1M セッションなら 800k）超過 → 引き継ぎドキュメント作成と後継セッション立ち上げを指示
5. 同一セッションへの重複トリガーを作らない。複数の指示は1つに統合する

### 報告形式

- 変化がなければ **1行**（例:「変化なし（8セッション）」）
- 変化があった項目のみ簡潔に記載
- **ユーザーがやるべき作業がある場合は、それを最上部に箇条書きで明示する**
- PR・セッションは URL を併記する
  - PR → `https://github.com/<owner>/<repo>/pull/<番号>`
  - セッション → `https://claude.ai/code/session_XXXXX`

## AIリソース節約

| 項目 | 対策 |
|------|------|
| 巡回の一本化 | 監視セッションは1本だけ。重複する監視系は停止する |
| 変化なしのスキップ | 進捗のないセッションは1日1回だけ確認し、毎時の巡回対象から外す |
| バッチ取得 | `list_sessions` / `list_triggers` の一括APIをまず使い、必要な差分のみ `get_session` で深掘りする |
| Agent の抑制 | 単純な状態確認は直接ツール呼び出し。大量の分析・分類のみ Agent に委任 |
| トリガー整理 | スケジュールのないトリガー（`next_run_at` が `0001-01-01`）は永久に発火しないので削除する |
| アーカイブ | 完了・長期停滞セッションは `archive_session` して巡回対象から外す |
| モデル選択 | 進捗確認・分類は軽量モデル、設計判断のみ上位モデル |
| 出力の簡潔化 | 変化のない報告は1行に留める |
| コンテキスト管理 | 監視セッションが上限に近づいたら引き継いで作り直す（累積を防ぐ） |

## 過去の課題管理

発生した問題・解決策はリポジトリ内に記録し、再発を防ぐ（トラブルシューティング記録／ナレッジベース）。

## トラブルシューティング

| 問題 | 原因 | 解決 |
|------|------|------|
| トリガーが発火しない | `cron_expression` も `run_once_at` も未設定 | `update_trigger` でスケジュールを設定、または削除して作り直す |
| トリガー実行されない | 過去の日時 | `update_trigger` で新しい日時に変更 |
| セッション消失 | - | トリガー自動無効化（`ended_reason: auto_disabled_session_gone`） |
| 子セッションアクセス失敗 | `persistent_session_id` 誤り | `list_sessions` で正確なID確認 |
| 監視セッションが重い | 同一セッションに巡回結果が累積 | 引き継いで新セッションで再開 |
| ネットワーク遅延 | - | 最大4回リトライ（2s → 4s → 8s → 16s） |
